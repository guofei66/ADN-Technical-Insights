一、背景

1.1 从单智能体到多智能体,再到编排器范式

单智能体系统(ReAct、Reflexion 一脉)的能力被三个边界锁死:一个上下文窗口、一条动作流、一条记忆流,而且串行执行使复杂长程任务时延高企。业界的应对是把任务切开、并发执行。Codex sub-agents、Claude Code agent teams、Copilot fleet、Kimi Agent Swarm 等先行框架不约而同采用 orchestrator–worker 结构:主代理负责规划、分解、分配、管理和整合。

这个结构在几个 worker 的规模上运转良好,但继续加人,协调与整合的负载全部压在编排器身上,编排器成为整个系统的扩展瓶颈——这正是 Anthropic 工程博客反复报告的多智能体协调痛点。Agensh 的立论由此而来:协调不应该是某一个智能体的能力,而应该成为基础设施的属性。

1.2 核心命题:增加智能体数量,提升组织智能

论文把 agent count 提到与模型规模、算力、数据并列的位置:在模型与底层 harness 不变的前提下,扩大自组织团队的规模即可提升"组织智能"。标题中的 1,024 就是这一命题的展示位——pandoc 任务上,从 1 个 agent 到 1,024 个 agent,最终测试通过率从 33.89% 升至 55.06%。

1.3 评测设置

基准为 ProgramBench:断网、6 小时预算、从零复现参考软件。论文选取其中最难的五个任务,模型固定为 GPT-5.6-sol (high),底层单智能体 harness 固定为 Copilot,唯一变量是 agent 数量 N ∈ {1, 8, 32, 128},pandoc 另测 1,024。

二、当前面临的问题

P1 单智能体的能力与时延天花板。一个上下文窗口、一条动作流,长程任务既做不好也做不快,复杂工作需要并行化。
P2 编排器成为规模瓶颈。中央编排器要规划、分解、分配、整合,容量有限;团队规模一大,收益就被编排器堵死,而且训练一个能干这件事的编排器本身代价不低(Kimi Swarm 即为此专门训练)。
P3 任务分配依赖中央规划。去掉编排器之后,谁来决定"接下来该干什么"、干到什么程度算完成?
P4 并发撞车与所有权冲突。多个 agent 同时改同一处,重复劳动、相互覆盖。
P5 知识孤岛与重复踩坑。一个 agent 验证过的结论、走过的死路,其他 agent 不知道,组织在为同样的学费反复买单。
P6 并发集成的正确性。多人改动如何安全汇成一份工作,错误贡献如何被拦住。
P7 长时程的组织稳定性。6 小时、成百上千成员,单个 agent 卡死或失败是否会拖垮全局。

三、论文如何解决

P1 多智能体异步并发解决单智能体天花板问题

单 agent harness 原样保留,每个 worker 内部仍是完整的 agentic loop;Agensh 在外层叠加组织行为,让 N 个对等 worker 并发推进,关键是完全异步——任何 worker 不等待其他 worker 完成整轮循环。这里的异步是严格含义:worker 之间没有同步屏障,消息与发现按各自的送达时机插入每个 worker 的回合,而不必等所有人跑完一轮。

结果:五任务平均通过率 1 agent 19.31%、8 agents 20.68%、32 agents 26.52%、128 agents 28.78%,相对提升约 49%。时延收益同样明确:pandoc 上突破 30% 通过率的时点,128 agents 约 30 分钟、32 agents 约 60 分钟、8 agents 约 90 分钟,单 agent 两个小时内始终未达标。加人同时改善终值与达标速度。

成效:达成质量与时延的双重改善。在模型(GPT-5.6-sol high)与底层 harness(Copilot)完全不变的前提下,仅靠扩大组织规模——
  • 五任务平均最终通过率 19.31% → 28.78%(+9.47 个百分点,相对提升约 49%),且五个任务整体同向上升,不是个别任务拉动的假象;
  • 达标时延显著压缩:pandoc 突破 30% 通过率的时点,128 agents 约 30 分钟、32 agents 约 60 分钟、8 agents 约 90 分钟,单 agent 两小时未达;
  • pandoc 扩至 1,024 agents:33.89% → 55.06%,千级规模仍单调受益。

P2 去中心化基础设施解决编排器瓶颈问题

全文的关键一步。Agensh 不是再造一个更聪明的编排器,而是把编排器的三类职责分别交给三件套基础设施:

编排器原职责外化到实现
持有全局任务状态共享工作区Gitea(Git):私有分支开发,PR 合并进 main,自带版本史、变更溯源、冲突检测,issue/PR 作为协作载体
在 worker 间传递信息消息接口Mattermost:公告频道(每轮循环开始时送达)+ 直连消息(每次工具调用返回时送达,可打断对方当前回合)
记忆与分发经验共享上下文DeLM 式追加型数据库,近期记忆窗口 + context grep 全史检索;新条目在其他 worker 下次工具调用返回时转发

两条配套设计原则值得单独记下。其一,协作协议写在提示词里而非硬编码进运行时——所有 worker 除 ID 外提示词完全相同,组织行为等于提示词,改协议不必改系统。其二,即插即用:Agensh 只是叠加层,通过轻量适配器可换底层 harness(Copilot、Claude Code)。

成效:达成千级规模、无中央协调。
  • 1,024 个 worker 的任务认领、沟通、集成全部经基础设施完成,不经过任何中央智能体,收益曲线未因规模增大而出现协作崩溃——标题命题"组织智能可扩展到 1,024"在结构上成立;
  • 协作协议全部写在提示词里,组织行为迭代不需要改动运行时;
  • 组织层与执行层解耦,底层 harness 经轻量适配器即插即用(Copilot、Claude Code)。

P3 自组织任务认领解决任务分配问题

每个 worker 在循环的第二步自己提出并认领子任务:先读共享目标、同伴进展与已有发现,判断"还缺什么",再把认领范围以 CLAIM 条目写入共享上下文。任务分解不再来自中央规划者,而是分布式涌现——每个 worker 基于局部视野做局部决策,由消息协商与合并门禁兜底纠错。质量由验收标准保证:循环第四步,worker 对照子任务的验收标准自检,不达标自动返工。认领以公开条目的形式存在,任务分配因此从一次性计划变成随时可修正的声明,任何 worker 都能据此看到组织当前的分工地图。

成效:达成无中央规划下的持续任务流。每轮循环结束时,worker 基于最新集成状态与同伴进展自行确定下一个子任务,组织无需预先分解;验收标准闭环兜底任务质量,"该做什么"与"做到什么程度算完成"都不再依赖中央判断,千级成员下任务流持续不断。

P4 可打断直连消息解决并发撞车问题

认领写入共享上下文后,重叠与冲突对全员可见。消息接口做了分级:一般公告走频道,每轮循环开始时批量送达;"我们俩要改同一个东西"这类急事走直连消息,在对方的工具调用返回时插入——等于打断对方当前回合,冲突在酿成浪费之前解决。合并时若遇冲突,worker 吸收同伴最新进展、解决后重新合并,重试内建于循环第五步。

轨迹里的实例:8 agents 规模,FFmpeg 上两个 worker 发现认领重叠,一方经沟通后主动转向互补工作;1,024 规模演化出更成熟的机制——请求方同时联系多个候选集成者,选首个有效响应者,取消其余请求。

成效:达成撞车在浪费发生之前解决。
  • 8 agents 即出现认领重叠的自主协商:FFmpeg 上两个 worker 沟通后,一方主动转向互补工作,无人仲裁;
  • 1,024 规模演化出竞速机制——同时联系多个候选集成者、选首个有效响应者、取消其余,冲突解决不依赖人工;
  • 合并冲突由 worker 吸收同伴最新进展后重合并,重试内建于循环,集成不因冲突停摆。

P5 类型化共享上下文解决知识孤岛问题

worker 随时发布五类短条目:OBSERVED(观察到的参考行为)、FACT(已确认事实)、FAIL(已证伪路线)、CLAIM(工作认领)、PATCH_SUMMARY(完成的修改,格式为 files / idea / evidence)。论文明确说 FAIL 是价值最高的条目——它阻止同伴在死路上继续消耗预算。把负面知识当作组织级机制来设计,而不是顺带为之,这是全文最值得抄的细节。context grep 保证超出近期记忆窗口的历史仍可检索,支撑 6 小时长程任务。

成效:达成负面知识的组织级共享。已证伪路线以 FAIL 条目写入即广播,同伴不再重复试错,预算集中到可行方向;可复用发现(FACT / OBSERVED)跨 worker 即时可见;context grep 保证 6 小时长程任务中,早期发现不因近期记忆窗口滚动而丢失。

P6 Git 门禁加涌现评审解决集成质量问题

所有贡献必须走"验证通过 → PR 合并"的门禁,Git 暴露文本冲突,由 worker 回溯解决。更关键的是轨迹中涌现的评审行为:32 agents 规模,PHP-src 上多个同伴批准某贡献,另一 worker 找到反例,审批撤回,作者修复,重新评审,第三方合并——完整的代码评审生命周期,没有任何流程预定义。128 agents 规模,worker 按既往经验挑选评审者并复用评审关系;pandoc 上协商出标准集成协议(交 commit hash 请同伴验证合并),失败后自主修订协议,改为授权同伴执行完整的更新、测试、检查、合并闭环。集成安全不靠中央把关,靠门禁加涌现的同行评审。

成效:达成无中央把关下的集成质量。
  • 32 agents 出现完整评审生命周期:多同伴批准 → 第三方找出反例 → 审批撤回 → 作者修复 → 重新评审 → 第三方合并,错误贡献被有效拦截;
  • 128 agents 评审走向专业化(按既往经验选择评审者并复用评审关系),集成协议标准化并被 worker 自主修订(授权同伴执行完整的更新-测试-检查-合并闭环)。

P7 同角色冗余与存活机制解决组织稳定性问题

运行时内建恢复与存活(liveness)机制,负责卡死检测与事件重派发。涌现层面,1,024 规模上多个 worker 同时担任集成者,同领域专家在他人失败后接手续作,组织不依赖任何单点。最终,千级成员、6 小时持续运转,收益曲线未出现协作崩溃。

成效:达成组织级容错。运行时 liveness 机制覆盖卡死检测与事件重派发;1,024 规模上集成者角色冗余,请求方"联系多个候选、选首个响应者",同领域专家在他人失败后接管续作——组织不依赖任何单点,千级成员 6 小时持续运转无协作崩溃。

四、对自动驾驶网络(ADN)的启发

ADN 当前主流范式同样是中心化编排:网络级编排器或 OSS 分解意图、下发策略、闭环管理。这与 Agensh 拆掉的那个 orchestrator 在结构上同构,正是本文对 ADN 的价值所在。

4.1 管理面转型为基础设施提供方,不再亲自分配任务

Agensh 最重要的启示:不要试图造一个更聪明的中央编排器来扩大自智化规模,而要把编排职责拆解为基础设施能力。映射到 ADN:共享工作区对应网络配置、脚本、模型的工作区,方向是配置即代码、PR 式变更流;消息接口对应跨域运维消息总线,方向是分级送达——常规告警批量走回合首,P1 故障走打断式直达处置 agent;共享上下文对应运维知识库,方向是从文档库升级为结构化、追加式、类型化、可全文检索的运维记忆。管理面瘦身为三件套的运营者,规模扩展的堵点随之消失。
电信应用场景:把全网基站的邻区、功率、切换参数迁移到"配置即代码"工作区,优化 agent 以 PR 形式提交参数变更,经仿真推演加现网灰度验收后合入;无线、传输、核心网三个处置域共用一条分级消息总线——P1 告警走打断式直达,日常参数稽核与通报批量走回合首;运维知识板沉淀全网根因结论与参数有效性证据,替代分散在各省份的 Excel 经验表。

4.2 FAIL 机制:已证伪方案全网广播,避免重复踩坑

电信运维早知案例库有价值,Agensh 给出了更锋利的设计:显式的 FAIL 条目——"此处置方案在此类故障上已证伪",写入即广播。大量重复故障处置成本正来自"换个区域又把已知无效的方案试了一遍"。把 FAIL 做成知识板的一等条目类型、配合全文检索,是低成本高收益的改造。
电信应用场景:故障处置知识库增加"反模式层"——"对该类掉话告警重启基带板无效""此退服方案在 V3 版本基站引发乒乓切换"等已证伪方案写入即全网广播;割接方案库同理,失败割接方案标记 FAIL,防止其他地市复用;多省共享同一知识板,避免 A 省踩过的坑 B 省再踩一遍。

4.3 借 Git 门禁管变更,生产网络须加审批与回滚

"验证通过才可合并、冲突显式化"这套流可以直接借鉴;但要认清关键差异——论文场景是离线复现任务,合并坏了可以回滚重试,ADN 的合并对象是生产网络,变更即影响业务。ADN 版的合并门禁要在测试通过之外强制附加影响评估、灰度或金丝雀发布、回滚预案。"worker 自行合并"在 ADN 应降级为"worker 发起、门禁裁决"。
电信应用场景:基站软件版本升级、核心网网元割接、切片配置变更全部走"agent 发起 + 门禁裁决"——变更 PR 强制附带影响评估(波及小区数、用户数、KPI 风险面),按"单站→簇→区域"灰度推进,回滚预案作为合并前置条件;夜间割接窗口由 agent 组织自动执行灰度推进与验证,指标超差自动回滚并上报。

4.4 同角色冗余与竞速接管,提升自愈组织容错能力

1,024 规模上演化出的两个机制可直接转译为 ADN 高可用设计。同角色冗余:多个 agent 同时具备处置能力,请求方联系多个候选、选首个有效响应者、取消其余——本质是把服务发现与负载均衡的原则用于 agent 组织。专家接手:同领域成员在他人失败后接管续作,故障不再绑定单点。落到网络自愈:处置 agent 按领域(无线、传输、核心网)形成冗余池,配合 liveness 心跳与任务重派发。自愈的"自"不仅指网络,也指 agent 组织本身。
电信应用场景:核心网宕机、传输中断等重大故障处置组建冗余编队——无线、传输、核心网各领域保持多个可用处置 agent,首个有效响应者接管工单,失败由同领域成员接续;台风、地震等灾害导致批量退服时,数百个抢修子任务(基站复位、传输倒换、油机发电调度)由 agent 组织自组织认领、互不等待。

4.5 扩容压缩达标时间,直接改善 MTTR

加人不只提升终值,更压缩达标时间(30% 阈值在 30、60、90 分钟间随规模前移)。对 ADN,这一性质比最终通过率更值钱:故障处置有硬性 SLA,MTTR 是核心指标。重大故障场景下临时扩容处置 agent 编队,是模型不变的条件下压缩 MTTR 的可用杠杆。
电信应用场景:重大保障与硬 SLA 场景——节假日高铁枢纽话务高峰、重大活动通信保障、灾后网络恢复:在模型与编队能力不变的前提下,临时扩容处置 agent 编队(如 32→128),把"恢复度提前 30-60 分钟达成"直接转译为 SLA 达标率与用户投诉量的改善。

4.6 规模不是越大越好,先算成本账再定编队

128 到 1,024 在 pandoc 上仅再加 4.12 个百分点,边际收益急剧递减,而全文未报告 token 成本——1,024 个 agent 跑 6 小时是巨量开销。ADN 是成本敏感行业,教训直接:规模化前先建成本-收益曲线,找到性价比拐点(本文数据暗示在 128 附近),以 8→32→128 阶梯推进试点,每档记录"每单位 MTTR 改善的 token 成本"。
电信应用场景:建立"告警等级 × 组织规模"的调度矩阵——日常巡检与小故障由 8-32 个 agent 的常驻小编队处理,P1 重大故障或重大保障再弹性扩容至 128;每一档沉淀"每单位 MTTR 改善的 token 成本"账目,作为扩容决策依据,避免为低价值告警烧大编队。

4.7 协作规程写进提示词,运维流程可热更

协作协议放在 worker 提示词里,worker 甚至自发修订了集成协议。对 ADN,跨域协同处置规程(谁评审、谁合并、谁通报)可以做成可热更的组织章程配置,而不是写死在流程引擎里;允许 agent 在运行中协商出更优规程后,经人在环节审批固化为新章程。
电信应用场景:跨域联动处置规程(无线-传输-核心网故障联动中谁定位、谁评审、谁执行、谁通报)做成可热更的"组织章程"配置——某次重大割接中 agent 协商出更优的校验顺序,经专家评审后固化为新章程,流程引擎无需发版;不同省份、不同网络制式可维护各自的章程版本。

4.8 建设网络版评测基准,用数据指导扩编

Agensh 的说服力很大程度上来自评测设计:断网、限时、从零复现、客观判分。ADN 可类比构造故障注入与意图复现基准:给定目标网络状态或故障场景,断开历史工单检索,限时让 agent 组织恢复或达成,以客观验收脚本判分,并测绘"agent 数量-达标时间-通过率"曲线。没有这样的基准,多智能体规模化只能停留在经验叙事。
电信应用场景:在数字孪生网络或实验室环境构建"网络版 ProgramBench"——注入标准故障集(单站退服、链路抖动、AMF 过载、切换失败率飙升),屏蔽历史工单,限时让 agent 组织恢复,以 KPI 恢复度(接通率、掉话率、时延回归基线)客观判分;测绘"agent 数量-达标时间-恢复率"曲线,为编队规模与保障资源决策提供依据。

4.9 论文与生产网络的四处差距,不能照搬

论文场景与生产网络有四处不能照搬。安全等级不同:软件仓库任务失败可弃,生产网络变更失败即事故,门禁与熔断必须比论文强得多(见 4.3)。论文未讨论失效或失控 worker 的级联风险,可打断消息在告警风暴下可能演变为打断风暴,ADN 需要打断限流、信誉隔离与熔断。任务可分解性假设:ProgramBench 任务天然可切分为模块级子任务,网络故障跨域根因耦合度高,自组织认领可能失效,需保留分层编排作为兜底——域内自组织加域间轻编排的混合形态,可能才是 ADN 的落点。可复现性:论文代码与项目页在检索时均未公开(404),liveness、事件路由等工程声称在落地前需自行验证。
电信应用场景:邻区删除、功率调整、割接指令等高危操作保留人在环节审批,agent 组织只到"发起 + 论证"为止;重大故障告警风暴下启用打断限流与 DM 熔断,防止处置 agent 被消息淹没;VoNR 掉话这类横跨无线、核心、传输的耦合根因,保留分层编排兜底,域内才放开自组织。

五、小结

Agensh 用三步把多智能体组织从十级推到千级:拆掉编排器、把协调外化为三件套基础设施、把协作协议写进提示词。对 ADN 而言,最有迁移价值的不是"1,024 个 agent"这个数字,而是三条设计原则——协调能力做成基础设施、FAIL 式负面知识共享、同角色冗余与竞速接管。落地路径:先建评测基准,再以 8/32/128 阶梯试点,门禁升级为"影响评估 + 灰度 + 回滚",架构走向域内自组织与域间轻编排的混合形态。
