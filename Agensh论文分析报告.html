1. 一句话总结(TL;DR)

Agensh 是微软研究院提出的去中心化、无中央编排器(orchestrator-free)的多智能体组织框架:1,024 个对等 worker 在共享基础设施(Git 工作区 + 消息接口 + 共享上下文)之上自组织地认领子任务、行动、验证、合并;在 ProgramBench 五个最难软件复现任务上,把智能体数量当作一个新的扩展维度(scaling dimension)——1→128 agent 使平均测试通过率从 19.31% 提升到 28.78%(相对提升约 49%),pandoc 任务上 1→1,024 agent 从 33.89% 提升到 55.06%,且更大组织更早达到同等性能(更低时延)。

2. 研究背景与动机

2.1 单智能体的三重天花板

单智能体系统(ReAct、Reflexion 一脉)受限于: - 一个上下文窗口(context window) - 一条动作流(action stream) - 一条记忆流(memory stream)

串行执行对复杂长程任务带来高时延。突破方向自然是多智能体并行。

2.2 现有多智能体 harness 的瓶颈:中央编排器

论文点名对比的先行框架: - Codex sub-agents:委派并行 worker,结果回传父代理汇总; - Claude Code sub-agents / agent teams:围绕固定的 lead 会话派生、管理共享任务、传递消息; - Copilot fleet(/fleet 命令); - Kimi Agent Swarm:训练编排器做任务分解与并发调度。

共同结构是 orchestrator–worker:主代理负责规划、分解、分配、整合。问题在于——整个系统的可扩展性被编排器的管理、协调与整合能力卡死(这也是 Anthropic 工程博客中反复报告的多智能体协调痛点)。Agensh 的立论:去掉中央编排器,让协调本身分布化。

3. 方法:Agensh 的设计

3.1 核心:五步异步协作循环(Cooperation Loop)

每个 worker 独立、并发、异步地执行同一循环,彼此不等待:

步骤 内容 关键机制
1 Gather context 读取共享目标、当前状态、同伴进展、消息与已有发现,与环境交互规划下一步 —
2 Claim sub-task 自己提出并认领子任务,以 CLAIM 条目写入共享上下文 子任务发现与分配完全自组织
3 Take action 本地干活;随时把可能有用的新发现写入共享上下文 中途成果即时共享
4 Verify results 对照子任务验收标准自检,不达标则返工 验收标准驱动
5 Merge progress 把贡献合并进共享工作区,发布变更说明(改了什么/思路/验证证据);冲突则吸收同伴最新进展、解决后重合并 Git PR 流程

循环回到第 1 步,基于最新集成的进展认领下一个子任务。协作的全部智能被压进 worker 的提示词(所有 worker 提示词除 worker ID 外完全相同),而不是硬编码在运行时里——这是"自组织"声明的实现基础。

3.2 三件套基础设施(Agentic Organization Infrastructure)

(1)共享工作区(Shared Workspace) - 用 Gitea(Git 平台)承载:私有 checkout/分支开发 → PR 集成进 main; - Git 天然提供:并发写入、异步读取、版本历史、变更溯源、文本合并冲突暴露给 worker 自行回溯解决,外加 issue/PR 作为协作载体。

(2)消息接口(Message Interface) - 用 Mattermost 实现,双通道分级: - 共享任务频道(announcements):低优先级,在每轮循环开始时批量送达; - 直连消息(DM):高优先级,在每次基础设施工具调用结束时送达——即能打断 worker 当前回合,是解决认领冲突的快速通道; - 保留会话历史、异步送达,同伴干活不被阻塞。

(3)共享上下文(Shared Context) - 思想来自 DeLM(arXiv:2606.10662,去中心化多智能体共享上下文),做了工具格式与指令适配; - 追加式(append-only)数据库 + 近期记忆窗口;类型化条目: - OBSERVED 观察到的参考软件行为 - FACT 已确认事实 - FAIL 已证伪的路线(论文称之为"价值最高的条目"——阻止同伴在死路上浪费预算) - CLAIM 工作认领声明 - PATCH_SUMMARY 已完成修改(格式:files= | idea= | evidence=) - context grep 工具:支持检索超出近期记忆窗口的全量历史,服务更长任务视界; - 新条目作为高优先级更新,在其他 worker 下一次基础设施工具调用返回时转发,实现跨组织即时可见。

3.3 实现架构:组织 harness 叠加在单智能体 harness 之上

  • Agensh 不替代单智能体 harness,而是外层组织层:底层 harness(实验中为 Copilot,亦宣称可通过轻量适配器接入 Claude Code 等)负责单 worker 的本地 agentic loop(会话状态、模型调用、工具执行);Agensh 负责组织级行为——worker 身份、协作协议、事件路由、健壮派发、工作区访问、消息、共享上下文、恢复与存活(liveness)机制;
  • 即插即用:协作循环以提示词工作流指令实现,耦合度极低;
  • 实测配置(附录 A):worker 命名 pbench-team1-worker1..1024,Gitea 容器内地址 http://gitea:3000,Mattermost 频道 pbench-task,board_write 发布共享上下文,每回合提示词中渲染 ==== SHARED CONTEXT ==== 段落。

4. 实验与结果

4.1 实验设置

  • 基准:ProgramBench(arXiv:2605.03546)——在断网 + 6 小时预算内从零复现参考软件行为;取其 200 个实例中 SOTA 平均通过率最低(最难)的 5 个任务:
任务 文件数 代码行数 代码体积 领域
FFmpeg 10,090 1,549,005 75.51 MB 多媒体处理
gromacs 8,982 815,539 47.30 MB 分子模拟
pandoc 2,767 104,336 4.86 MB 文档转换
PHP-src 26,266 2,812,757 119.76 MB 语言解释器
ctags 7,313 246,228 9.15 MB 代码索引
  • 固定变量:模型 GPT-5.6-sol(high)、底层单智能体 harness 为 Copilot、预算 6h;唯一变量是 agent 数量 N ∈ {1, 8, 32, 128}(pandoc 追加 1,024)。

4.2 主结果:智能体数量是新的扩展维度

五任务平均最终通过率(test-pass rate):

N 1 8 32 128
平均通过率 19.31% 20.68% 26.52% 28.78%
  • 1→128:+9.47 个百分点,相对提升约 49%;五任务整体呈上升趋势。
  • pandoc 扩展到 1,024 agent:33.89%(1)→ 50.94%(128)→ 55.06%(1,024);比 128 再 +4.12pp,比单 agent 共 +21.17pp(相对提升约 62%)。

时延收益(前 2 小时加速曲线): - 更大组织更早达到同等通过率。pandoc 上突破 30% 通过率的时点:128 agent @ 30 分钟;32 agent @ 60 分钟;8 agent @ 90 分钟;单 agent 前 2 小时内始终未达标。 - 即:加人不仅提升终值,还压缩达到同一性能的时间——对硬时延约束场景是关键卖点。

4.3 涌现的自组织合作(随规模分级)

这是论文第二贡献:轨迹分析显示,所有 worker 同 prompt 同循环,但组织形态随规模演化——

规模 涌现行为 实例
8 同伴协调 gromacs:先公告模块接口,再各自独立实现兼容的命令模块;FFmpeg:发现认领重叠后经沟通一方主动换赛道
32 多人集成管理 PHP-src:多个同伴批准某贡献 → 另一 worker 找到反例 → 撤回批准 → 作者修复 → 重新评审 → 第三方合并(完整代码评审生命周期)
128 专业化 + 工作流标准化 按既往经验挑选评审者并复用评审关系;pandoc 上协商出标准集成协议(作者更新测试分支 → 交 commit hash 给同伴验证合并),失败后迭代修订协议(改为授权同伴执行完整 update-test-check-merge 闭环)
1,024 组织级角色分化 多个 worker 同时扮演 integrator(集成者);请求方同时联系多个候选集成者、选首个有效响应者、取消其余——同角色冗余带来容错:某 worker 失败后,同领域专家可接手,组织不再依赖单点

值得注意的解读:智能体组织在没有任何中央设计的情况下,自发重新发明了人类软件工程实践——接口先行的分工、code review、审批撤回、集成协议、专职集成者/容错冗余。这是论文最具传播力的观察,但注意它目前是定性叙事,未给出量化涌现指标(见 §6 批判)。

5. 贡献与定位

5.1 核心贡献

  1. 架构贡献:首个(公开报道中)明确以"去编排器"为目标并实证扩展到 1,024 agent 的多智能体软件工程 harness;协调负载从编排器转移到"成熟基础设施(Git + IM + 追加式共享上下文)+ 同构 worker 提示词"。
  2. 实证贡献:在极难的长程任务(百万行级代码库从零复现)上给出 N=1/8/32/128(及 1,024)的扩展曲线,同时报告质量(最终通过率)与时延(达标时间)两个轴的收益。
  3. 概念贡献:"智能体数量"被提为与模型规模、算力、数据并列的又一扩展维度——"组织智能(organizational intelligence)"可随 N 扩展,直指通用智能前沿。
  4. 机制观察:给出随规模分级涌现的合作形态学(协调→集成→标准化→角色分化),为多智能体组织研究提供了可复用的描述框架。

5.2 与相关工作的差异

  • vs 编排器系(Claude Code teams / Codex / Kimi Swarm):去掉固定 lead/父代理;任务发现、依赖协调、结果整合由对等 worker 自担。
  • vs DeLM:直接继承其共享上下文思想(append-only + 近期记忆),扩展了 context grep 与类型化条目协议,并把规模推到千级。
  • vs Carlini 的"16 个 Claude 写 C 编译器":同为去中心化 Git 协作(Git + 任务锁文件 vs Gitea + PR),Agensh 增加了消息接口与共享上下文两类协调机制,并做了系统化的规模扫描与基准评测。
  • vs STORM(状态管理式共享工作区):STORM 在写入时强制状态一致性/检测过期编辑;Agensh 则依赖 Git 冲突暴露 + worker 自行回溯解决,更"社会性"、更少运行时强约束。
  • vs ChatCollab / SlackAgents:同样用 IM 承载协作,但 Agensh 的 DM 可打断 worker 当前回合,这是低时延冲突解决的关键设计。

6. 批判性评估

6.1 优点

  1. 问题选得准:编排器瓶颈是当前多智能体产品(各类 sub-agent/fleet 功能)真实遇到的工程天花板;去中心化自组织是合理的下一站。
  2. 工程上极度务实:没有发明新中间件,直接组装 Gitea + Mattermost + DeLM 式上下文板;协作循环写在提示词里,使框架对底层 harness(Copilot / Claude Code)保持即插即用——工业界可低成本复现。
  3. 两个收益轴都报告了:不只报终值提升,还报"更快达到同一水平",后者对企业场景(发布窗口、故障恢复时限)往往更值钱。
  4. 对负面知识的重视:FAIL 条目被称为"价值最高"——这是对多智能体重复踩坑问题的直接回应,值得所有多智能体框架借鉴。
  5. 评测任务够硬:百万行级、断网、6 小时预算、从零复现,远超一般 SWE-bench 式局部修改任务。

6.2 局限与效度威胁

  1. 成本缺失(最大短板):1,024 agent × 6h 的 token/算力成本全文未给出。128→1,024 线上 pandoc 仅 +4.12pp,收益急剧边际递减;每百分点通过率的成本很可能在 N 增大时爆炸。缺成本归一化曲线,"scaling dimension"的叙事就缺了与模型 scaling law 对话的关键一环。
  2. 无同规模编排器基线对比:论文声称编排器是瓶颈,但没有在相同 N(如 32/128)下与 Claude Code agent teams / Kimi Swarm 等编排式框架对打——"去编排器更好"目前只在与单 agent 的对比中体现,属于必要非充分证据。
  3. 无组件消融(至少正文未见):共享上下文开/关、DM 打断机制开/关、CLAIM 冲突协议、liveness 机制各自贡献多少?五步循环是整体打包引入的。
  4. 评测广度:5 个任务 × 1 个模型 × 1 个底层 harness;正文未报告跨种子方差/置信区间,单次运行的可能性无法排除;而 ProgramBench 此类长程任务方差通常很大。
  5. "涌现"的证据等级:四档涌现行为来自轨迹的定性解读,无网络分析(通信图)、无角色分化度量、无协议标准化率等量化指标;且五步循环与类型化条目本身就在提示词里强烈引导了这些行为——是"涌现"还是"脚手架的忠实执行",边界模糊。
  6. 数据污染疑点:FFmpeg、pandoc、PHP 都是著名开源项目,模型权重大概率见过其源码;"断网"只挡住检索,挡不住参数化记忆。该效度问题继承自 ProgramBench,论文未讨论。
  7. 千级规模的协调成本未量化:1024 个 writer 的 Git 文本冲突率、消息扇入(理论 O(N²) 风险)、共享上下文噪声(1024 个 worker 互发更新)——论文讲了机制,没给负载/噪声数据。
  8. 终止与止损:循环"直到目标达成"——组织如何判定收尾?平台期后 6 小时预算的浪费比例未报告。
  9. 可复现性缺口:论文挂出代码与项目页链接,但截至检索时均为 404;对这类工程系统论文,复现依赖开源,目前无法验证。
  10. 鲁棒性话语:提到同角色冗余容错,但未讨论故障级联(DM 打断风暴)、"恶意/失控 worker"、拜占庭行为等去中心化系统经典风险。

6.3 总体评价

这是一篇工程系统论文(也算概念验证论文),而非严格意义的 scaling law 论文:它没有拟合扩展律函数形式,也没有算力对齐的对照实验,却被置于"新的扩展维度"的宏大叙事下——标题与证据强度之间有落差。但就"证明 1,024 个 LLM agent 能在无编排器条件下组织起来并单调受益"这一目标而言,证据是令人信服的,且给出的基础设施三件套 + 提示词化协作协议是当下可复用性最高的部分。预计对 agent harness 产品设计(尤其是去编排化、FAIL 共享、可打断 DM)有直接参考价值。

7. 实践启示(面向工程团队)

  1. "加人"第一次有了实证背书:在时间预算硬约束的任务上,水平扩容 agent 数量是同模型条件下可用的性能/时延杠杆——不必先升级模型。
  2. 去编排化的最小可行架构 = Git + IM + 追加式上下文板:三者都是现成件;真正需要自己写的只有事件路由、健壮派发与 liveness。
  3. 消息分级送达是低成本高价值设计:公告走"回合首"、急件走"工具调用后打断",模拟了人类团队的异步/同步沟通分层。
  4. 把 FAIL 当一等公民:显式记录并广播已证伪路线,是多智能体系统里性价比最高的共享知识。
  5. 提示词即组织章程:协作协议不进运行时,放进 prompt——迭代组织行为只需改提示词,论文中"集成协议被 worker 自行修订"正是这种松耦合的产物。
  6. 预算编排:按论文的边际递减曲线,128 附近可能是性价比拐点;大规模编排应先做成本-收益测算,而非直接冲 1,024。

8. 开放问题与后续研究方向

  1. 成本归一化的扩展曲线:token 开销、每 pp 通过率成本 vs N;是否存在经济性最优 N。
  2. 等规模对照:去中心化 vs 编排式 vs 混合(分层自组织)在同 N、同预算下的系统对比。
  3. 组件消融:共享上下文 / DM 打断 / CLAIM 协议 / liveness 各自的因果贡献。
  4. 涌现的定量化:通信图拓扑演化、角色分化指数、协议复用率、评审网络形成率。
  5. 异构组织:不同模型/不同底层 harness 混编的同一组织(性价比分工)。
  6. 千级以上的协调瓶颈:消息扇入、共享上下文检索质量、Git 冲突率随 N 的增长规律。
  7. 安全与失控:失效 worker、打断级联、资源耗尽型行为的防护机制。
  8. 泛化:从"软件复现"到研究、运维、数据分析等其他长程协作领域,结论是否平移。

9. 关键数据速查

  • 五任务平均最终通过率:1→19.31% / 8→20.68% / 32→26.52% / 128→28.78%(+9.47pp,相对 +49%)
  • pandoc 最终通过率:1→33.89% / 128→50.94% / 1,024→55.06%(相对 1 agent +62.5%)
  • pandoc 达到 30% 通过率的时长:128 agents≈30min,32≈60min,8≈90min,1 agent>2h 未达
  • 固定配置:GPT-5.6-sol(high)+ Copilot harness + 6h 预算 + 断网
  • 基础设施:Gitea(工作区)+ Mattermost(消息)+ DeLM 式共享上下文(append-only + context grep)
  • 条目类型:OBSERVED / FACT / FAIL / CLAIM / PATCH_SUMMARY
